# Engineering Delivery Pipeline（深度工程交付流水线）

> **用途**：把一次"完整软件功能/需求交付"自动跑成全生命周期工程流水线，取代"用户每走一步手动叫下一个技能"。你（执行模型）在本技能激活后是**流水线驱动者**：按序激活各阶段技能、把上一阶段产出作为下一阶段输入、在产物中推进，而不是贴完代码就停下等指令。

## 〇、门卫判定：何时激活本技能

**Description 已充当入口判断；进入正文后再次自检：**

- ✅ **激活**：新建/开发完整功能或应用、全栈业务实现、数据库表结构演进、微服务/模块编排、复杂重构、生产级 Bug 排障；或用户口令命中（见下）。
- ❌ **绝不激活（硬排除）**：纯概念/原理科普、命令/语法/配置查询、文档翻译、浏览已有代码、单行脚本、≤10 行且不影响架构的微调。此类一律直答或走轻量实现，禁止启用流水线。
- 若处于边界（"先讲讲再动手"）：先答概念，再询问是否进入深度交付，不擅自启动。

## 一、口令（双控覆盖低置信边界）

| 意图 | 用户可能表述 | 行为 |
| :--- | :--- | :--- |
| **进入** | "深度交付 / 完整流程 / 全流程开发 / 整套流程跑一遍 / 正式开发 X" | 无条件进入流水线，即便特征模糊 |
| **退出/取消** | "退出完整流程 / 取消当前方案 / 这个作废 / 不需要那么重 / 停" | 立即释放进度，回到直答或轻量模式 |
| **中途降级** | "只要个思路别走流程 / 先简单做一下" | 停流、跳到轻量实现，已落盘产物保留备查 |

用户没说口令但特征命中时，自动进入，但**首条产出必须先给 3 行以内的"我将执行的流程摘要"**，让用户来得及喊停。

## 二、两处人工确认点（只卡方向，不催进度）

确认点是**让用户拍板内容方向**，批准后自动续跑下一阶段，**不需要用户指示"下一步用什么技能"**：

- 🔴 **确认① = S1 审讯结束**：以 `requirements.md` 需求摘要形式呈现边界/假设/分支，请用户确认或修改。
- 🔴 **确认② = S3 计划批准**：以 `implementation_plan.md` 呈现任务切分/依赖/检查点，请用户批准或修改。

两处之间、以及确认②之后直到交付，全程自动推进、逐阶段宣告。

## 三、状态锚定（跨轮不丢进度）

不依赖对话记忆判断"现在到哪了"，**以落盘产物为准**：

- **每轮开始时**，先查最新产物文件（按下方清单），据其确定当前阶段与下一步，绝不重新从头审讯。
- **产物清单**：
  - S1 → `docs/superpowers/specs/YYYY-MM-DD-<feature>.md`（需求摘要）
  - S3 → `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`（实施计划）
  - S6 → 终端输出测试全绿证据 + `repo-security-sanitizer` 扫描结果
- **每阶段完成时显式宣告**：`State N 完成 → <产物路径>，下一步自动进入 State M`。
- 若产物文件缺失（被删/改名/跨会话），以会话内最近已确认内容为准并提示用户进度可能丢失。

## 四、7 阶段流程（单向推进）

> 进度只进不退；唯一回退支线 S4↔S5（编码遇错进排错、修复回归）。方向性错误（需求理解偏差）不在此列——由确认①/② 把住，发现方向错了就带证据回到对应确认点重审，禁止硬闯错误方案。

| 阶段 | 目标 | 激活技能 | 产出/推进 |
| :--- | :--- | :--- | :--- |
| **S1 审讯** | 锁定业务边界/隐性假设/设计分支 | `grill-me`（重需求）/`brainstorming`（开放式） | 产出 `requirements.md` → **停：确认①** |
| **S2 调研与极简架构** | 检索开源标杆，七阶极简防过度设计 | `github_homework_researcher` + `ponytail` | 架构选型摘要 → 确认①后自动进 |
| **S3 计划** | 高可执行实施计划（任务/依赖/检查点） | `writing-plans` | 产出 `implementation_plan.md` → **停：确认②** |
| **S4 编码** | 红绿循环 TDD + 领域伴随 | `test-driven-development`；伴随：涉及库→`database-migrations`、容器→`docker-patterns`、鉴权/接口→`security-review` | 全绿测试 → 自动进 S6 |
| **S5 排错** | 根因定位后修复，禁盲猜 | `systematic-debugging` + `safe_code_repair` | 稳定复现命令 → 修复 → 回归 S4 |
| **S6 核验与脱敏** | 客观证据 + 密钥地毯扫描 | `verification-before-completion` + `repo-security-sanitizer` | 全绿证据 + 扫描报告 → 自动进 S7 |
| **S7 收尾** | 清理、合并、交付 | `finishing-a-development-branch`（如涉多分支/工作树配合 `using-git-worktrees`） | 交付验收（见 §6） |

## 五、执行铁律

1. **先技能后动作**：进入任一阶段，先激活对应技能并遵守其流程，再动代码。
2. **TDD / DRY / YAGNI / KISS**：测试先红后绿；最小实现；不为想象的需求扩功能。
3. **阶段宣告**：`Using engineering-delivery-pipeline → State N（<技能名>）：<本次动作>`
4. **童子军法则**：路过代码如有坏味道，先重构再扩展。
5. **禁止跳阶段与自发逆行**；发现需回退到 S1 的方向性问题时，先给用户证据，回确认点重审。
6. **危险动作不静默**：`merge`/`push`/删除文件/改库迁移等一律不替你决定，交由平台权限确认与用户拍板。
7. **零死角留痕**：关键产出写入 §三 产物路径，便于中断恢复与复盘。

## 六、收尾与交付

S7 完成后，输出交付摘要（改了哪些文件、测试证据、遗留事项），请用户验收。验收通过即本次交付结束，回到普通交互；用户后续追加需求默认作为**新交付**走同一条流水线，除非明确是轻量修改。
